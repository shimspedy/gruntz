## Build and configuration

1. [ ] **HIGH — the repo's only quality gate is red.** `npm run typecheck` exits 2:

   ```
   website/astro.config.mjs(2,30): error TS2307: Cannot find module 'astro/config'
   website/astro.config.mjs(3,21): error TS2307: Cannot find module '@astrojs/sitemap'
   ```

   `tsconfig.json` sets only `extends` and `strict` — no `include`/`exclude` — so the root
   `tsc` walks into `website/`, which is a **separate package** with its own `package.json`
   *and* its own `tsconfig.json`, and whose dependencies live in `website/node_modules`.
   `npm run check` is `typecheck && site:build`, so it fails at step one and never reaches
   the site build at all. With no test suite and no linter in this repo, typecheck is the
   *entire* safety net, and it has been failing — which trains everyone to ignore it and
   hides any real type error that appears later behind the same red output.
   The app's own source is currently clean; these two are the only errors.

2. [ ] **MEDIUM — the app declares Always-location permission it never requests and could
   not use.** `app.json` configures the `expo-location` plugin with
   `locationAlwaysAndWhenInUsePermission`, and the generated `ios/.../Info.plist` carries
   both `NSLocationAlwaysAndWhenInUseUsageDescription` and `NSLocationAlwaysUsageDescription`.
   But nothing in `src/` ever calls `requestBackgroundPermissionsAsync`, there is no
   `UIBackgroundModes` entry anywhere, and Android declares only `ACCESS_COARSE_LOCATION`
   and `ACCESS_FINE_LOCATION` — no `ACCESS_BACKGROUND_LOCATION`, no foreground-service
   permission. So the app asks App Review to justify Always-location for a capability it
   does not have. Two consequences: it invites a review clarification or rejection, and it
   is the configuration-level reason the known background-GPS problem cannot be fixed in
   the hook alone. (`ios/` is not tracked in git, so `app.json` is the source of truth.)

3. [-] **Secrets are handled correctly.** `secrets/` is gitignored and untracked, and
   `play-service-account.json` is mode 0600. A scan of every tracked file for private keys,
   RevenueCat keys and Google API keys found nothing: `src/config/monetization.ts` reads all
   four RevenueCat values from `EXPO_PUBLIC_*` env with empty-string fallbacks.

4. [-] **`NSMotionUsageDescription` is justified.** The app genuinely uses motion:
   `useRunTracker.ts` watches `Pedometer` and `useBarometerAltitude.ts` reads `Barometer`.

## Workout session and logging

5. [ ] **HIGH — a plan-day exercise with prescribed warm-ups can never be completed, and is
   silently dropped from the saved workout.** *Verified myself.* `startPlanDay` builds the
   working sets, then `sets.unshift(...)` prepends the warm-up rows **into the same array**,
   and only then sets `requiredSets: sets.length` — so `requiredSets` counts the warm-ups.
   `isExerciseDone` counts only `done && !warmup` sets, so 3 working sets can never reach a
   required 5. Consequences: the exercise never gets its check bubble, the header reads
   "6 sets to complete" for 3 working sets, the Finish button never appears (`allDone` is
   never true — the user has to hunt "Finish early" in the ⋯ menu), and `buildMission`'s
   `completed = s.exercises.filter(isExerciseDone)` **excludes the exercise entirely**: no XP,
   no PR check, absent from the mission record. A fully logged exercise vanishes from the
   saved workout. *Scale verified against the catalog: 591 exercise slots across 184 plan
   days in 47 of 528 plans.* `useSessionStore.ts:319` (after the `unshift` at `:317`);
   consumers `:218`, `:500`, `WorkoutSession.tsx:134`. Note `addWarmupSets` (`:396-419`) does
   it correctly — it prepends without touching `requiredSets`. Only `startPlanDay` is wrong.

6. [ ] **HIGH — PR detection compares weights across units without converting.** *Verified
   myself.* `ExerciseLogEntry.unit` is documented as "the user's setting when they lifted it",
   and `summarize()` converts correctly (`useExerciseLogStore.ts:100`,
   `toUnit(st.weight, entry.unit, unit)`). But `buildMission` compares
   `bestEffort(e.kind, done)` — live session weights in the *current* unit — against
   `bestEffort(e.kind, entry.sets)` on raw history weights, with no `toUnit` anywhere on that
   path. Worked example: 100 lb bench in history, user switches to kg, lifts 45 kg (≈99 lb) —
   `estimated1RM(45,·)` never beats `estimated1RM(100,·)`, so they **never get a PR again**.
   Reverse: 45 kg history, switch to lb, lift 100 lb → a false PR on every weighted exercise,
   plus `pr_bonus = prCount * 25` XP (`:552`) they did not earn. The Records/Charts tabs *do*
   convert, so the PR badge and the Records tab contradict each other about the same lift.
   `useSessionStore.ts:205-215`, `:512-520`.

7. [ ] **MEDIUM — swapping an exercise leaves the previous one's note in the box, and typing
   writes it onto the new exercise.** `ExerciseInsights` seeds `useState(savedNote)` once;
   `logKey` changes when `replaceExercise` swaps `exerciseId`, but the FlatList item key
   (`e.key`) does not, so the component never remounts and `note` is never re-synced.
   `saveNote` then persists the old movement's text under the new `logKey`, overwriting
   whatever was there. `ExerciseInsights.tsx:71-81`, swap at `:64-68`, key at
   `WorkoutSession.tsx:367`.

8. [ ] **MEDIUM — `replaceExercise` drops the un-logged rows but keeps the old
   `requiredSets`.** `const keep = logged.length ? logged : e.sets` — once any set is ticked,
   the swap keeps only the *done* rows and discards the remaining prescribed rows and their
   pre-filled weights, while `requiredSets: Math.max(logged.length, e.requiredSets)` stays at
   the original count. Swap after 1 of 4 sets → one row on screen, "4 sets to complete" on the
   label, and the exercise can never be marked done without tapping "Add set" three times.
   `useSessionStore.ts:440-458`.

9. [ ] **MEDIUM — the `programmaticScroll` guard leaks, so one real swipe after every index
   change is swallowed.** `onViewable` returns at `:178` (`first.index === getState().index`)
   *before* the reset at `:179-182`, so after any programmatic move (bubble tap, the 650 ms
   auto-advance, a width change) the flag stays `true`; the next genuine swipe clears it and
   returns without calling `setIndex`. The pager then shows exercise N+1 while the store index
   is N: wrong bubble highlighted, the visible page's video does not play
   (`active={visible && page === index}`), the stopwatch opens the rest sheet for the wrong
   exercise, and auto-advance targets from the wrong position. Self-corrects on the second
   swipe. `WorkoutSession.tsx:164-185`.

10. [ ] **MEDIUM — set values commit only on blur, so ticking ✓ with the keyboard up logs the
    prescribed number instead of what was typed.** `SetRow` holds typed text in
    `valueDraft`/`weightDraft` and calls `onChange` only from `onBlur`/`onSubmitEditing`
    (`SetTable.tsx:207-220`). The page ScrollView uses `keyboardShouldPersistTaps="handled"`
    (`WorkoutSession.tsx:486`), so tapping ✓ does not blur the input; `toggleSet` sees
    `st.reps == null` and `filled()` substitutes `previous[...]` or `ex.reps`. Type 12 into an
    empty reps cell, tap ✓ → the store records the prescribed 10 while the cell still shows
    12. It self-heals on a later blur, but not if the next tap is Finish / Finish early (both
    outside that ScrollView) — the mission and the log then keep the prescribed number, not
    the athlete's. Fallback at `useSessionStore.ts:355-365`. *The code path is verified; the
    exact on-device focus behaviour of `keyboardShouldPersistTaps` is not, and there is no
    test suite to settle it — confirm on device before/after the fix.*

11. [ ] **MEDIUM — the summary's "Reps" counts warm-up reps; "Sets" and the saved mission do
    not.** `reps` filters only `st.done`, while `setsDone` on the line above filters
    `st.done && !st.warmup`, and `buildMission` also excludes warm-ups
    (`useSessionStore.ts:505-506`). On any day with warm-ups the completion screen shows
    roughly 16 extra reps per exercise versus what is stored in `completed_reps` and counted
    toward rep achievements. `SessionSummary.tsx:26-27`.

12. [ ] **MEDIUM — repeating the same routine or plan day twice in one day silently saves
    nothing.** `startRoutine`/`startPlanDay` set `workoutDayId` to `routine:<id>` /
    `plan:<planId>:<dayId>` and `missionDate` to today; `completeMission` dedupes on
    `${mission_date}:${workout_day_id}` and returns state unchanged. `save()` ignores that and
    proceeds anyway: it calls `finish()` (wiping the session) and navigates to Celebration
    with `xpEarned: after.current_xp - xpBefore` = 0. The second session of the day ends on a
    celebration screen reading **+0 XP**, with no mission or streak credit and no explanation.
    `RoutineDetailScreen:119-139` and `LibraryPlanDayScreen:51-63` have no "already done
    today" guard, unlike `WorkoutDetailScreen:69` which disables the CTA. Sets do still reach
    the exercise log, so history survives. `SessionSummary.tsx:38-53`, `useUserStore.ts:313-319`.

13. [ ] **LOW — the duration shown on the summary is not the duration saved.** `minutes`
    (`:30`) recomputes from a live 1 s clock, but `mission` is `useMemo(..., [s])` over the
    store object, so `duration_minutes` (`useSessionStore.ts:540-543`) freezes at whatever
    `Date.now()` was when the summary last re-memoised. Sit on the completion screen for ten
    minutes and it reads "35 min" while the workout is logged as 25 — and which you get
    depends on whether an unrelated store write happened to re-run the memo.
    `SessionSummary.tsx:22-30`.

14. [ ] **LOW — stale save-requirement copy.** `canSave = setsDone > 0`, but the footnote shown
    when it is false still reads "Complete every set of at least one exercise to save this
    mission." — left over from the `canSave` fix in `docs/ux-audit.md` item 18. The only
    guidance a stuck user gets is wrong; one tick of any single set is enough.
    `SessionSummary.tsx:35, 122-126`.

15. [ ] **LOW — hooks called after a conditional return.** `useState(picker)` and
    `useRoutineStore(...)` sit at `ExerciseDetailScreen.tsx:97-98`, below the
    `if (!ex) return ...` at `:60-67`. Not reachable today because `ex` derives from route
    params that do not change for a mounted screen, but any change that makes `ex`
    resolvable-later turns this into a hard "Rendered more hooks than during the previous
    render" crash.

16. [ ] **LOW — the notes store can evict the note being typed.**
    `if (keys.length > 400) delete next[keys[0]]` removes the oldest-*inserted* key, and
    updating an existing key does not move it in insertion order. A user with >400 saved notes
    editing their oldest note loses it on every keystroke. `useExerciseNotesStore.ts:16-24`.

17. [ ] **LOW — "Completed today" shown for a past date.** `completed` is correctly per-date
    (`claimed.has(`${params.dateKey}:${day.id}`)`), but the disabled CTA label is hardcoded
    "Completed today" whatever date is being viewed. `WorkoutDetailScreen.tsx:61-69`.

18. [-] **Checked and holding up in this area:** `finish()` resets via `{...initial}` including
    `restPrescribed`/`restSetId`, so a new `start()` cannot inherit another workout's
    prescribed rest, and every `start*` caller either has no active session or calls
    `discard()` first. `restOverrides`/`previous` are deliberately preserved, and
    `PreviousSet.unit` *is* converted correctly in `prevLabel` (`SetTable.tsx:41-52`). PR
    history is genuinely read before `finish()` writes today's entry, so today cannot beat
    itself. `useExerciseLogStore.record` dedupes on `${startedAt}:${e.key}`, so a re-entrant
    finish cannot double-log. Plan day ids are globally unique and plan-prefixed (checked
    across all 528 plans / 2012 days: zero duplicates, no stray colons), so
    `parsePlanSessionId`'s naive `split(':')` cannot cross-credit the wrong plan. `Tap` has a
    450 ms press lock, so Finish cannot be double-submitted. `summarize`/`toUnit`/`repMax` in
    `ExerciseProgress.tsx` convert correctly — the unit bug in #6 is confined to `bestEffort`.
