A fresh whole-app audit, run after `docs/ux-audit.md` closed 262 of its 267 findings.

Six read-only audits covering disjoint areas — workout session & logging; plans, programs
and library; onboarding, paywall and subscription; navigation, state and notifications; run
tracker, stats and scoring; UI, accessibility and copy — plus a build/config pass.

## Build and configuration

1. [x] **HIGH — fixed. The repo's only quality gate was red.** `tsconfig.json` now excludes `website`, `ai-proxy`, `android`, `ios` and `dist`; `npx tsc --noEmit` exits 0. (`npm run check` still needs `npm --prefix website install` for its site-build step — an environment gap, not a code defect.) Originally: `npm run typecheck` exits 2:

   ```
   website/astro.config.mjs(2,30): error TS2307: Cannot find module 'astro/config'
   website/astro.config.mjs(3,21): error TS2307: Cannot find module '@astrojs/sitemap'
   ```

   `tsconfig.json` sets only `extends` and `strict` — no `include`/`exclude` — so the root
   `tsc` walks into `website/`, which is a **separate package** with its own `package.json`
   *and* its own `tsconfig.json`, and whose dependencies live in `website/node_modules`.
   `npm run check` is `typecheck && site:build`, so it fails at step one and never reaches
   the site build at all. With no test suite and no linter in this repo, typecheck is the
   *entire* safety net, and it has been failing — which trains everyone to ignore it and
   hides any real type error that appears later behind the same red output.
   The app's own source is currently clean; these two are the only errors.

2. [x] **MEDIUM — fixed.** `locationAlwaysAndWhenInUsePermission` removed from the `expo-location` plugin config, so the build no longer asks App Review to justify a background capability the app does not have. Foreground tracking is unchanged. Originally: `app.json` configures the `expo-location` plugin with
   `locationAlwaysAndWhenInUsePermission`, and the generated `ios/.../Info.plist` carries
   both `NSLocationAlwaysAndWhenInUseUsageDescription` and `NSLocationAlwaysUsageDescription`.
   But nothing in `src/` ever calls `requestBackgroundPermissionsAsync`, there is no
   `UIBackgroundModes` entry anywhere, and Android declares only `ACCESS_COARSE_LOCATION`
   and `ACCESS_FINE_LOCATION` — no `ACCESS_BACKGROUND_LOCATION`, no foreground-service
   permission. So the app asks App Review to justify Always-location for a capability it
   does not have. Two consequences: it invites a review clarification or rejection, and it
   is the configuration-level reason the known background-GPS problem cannot be fixed in
   the hook alone. (`ios/` is not tracked in git, so `app.json` is the source of truth.)

3. [-] **Secrets are handled correctly.** `secrets/` is gitignored and untracked, and
   `play-service-account.json` is mode 0600. A scan of every tracked file for private keys,
   RevenueCat keys and Google API keys found nothing: `src/config/monetization.ts` reads all
   four RevenueCat values from `EXPO_PUBLIC_*` env with empty-string fallbacks.

4. [-] **`NSMotionUsageDescription` is justified.** The app genuinely uses motion:
   `useRunTracker.ts` watches `Pedometer` and `useBarometerAltitude.ts` reads `Barometer`.

## Workout session and logging

5. [x] **HIGH — fixed.** `requiredSets` is now captured *before* the warm-ups are unshifted, so it counts working sets only. Originally: a plan-day exercise with prescribed warm-ups could never be completed, and is
   silently dropped from the saved workout.** *Verified myself.* `startPlanDay` builds the
   working sets, then `sets.unshift(...)` prepends the warm-up rows **into the same array**,
   and only then sets `requiredSets: sets.length` — so `requiredSets` counts the warm-ups.
   `isExerciseDone` counts only `done && !warmup` sets, so 3 working sets can never reach a
   required 5. Consequences: the exercise never gets its check bubble, the header reads
   "6 sets to complete" for 3 working sets, the Finish button never appears (`allDone` is
   never true — the user has to hunt "Finish early" in the ⋯ menu), and `buildMission`'s
   `completed = s.exercises.filter(isExerciseDone)` **excludes the exercise entirely**: no XP,
   no PR check, absent from the mission record. A fully logged exercise vanishes from the
   saved workout. *Scale verified against the catalog: 591 exercise slots across 184 plan
   days in 47 of 528 plans.* `useSessionStore.ts:319` (after the `unshift` at `:317`);
   consumers `:218`, `:500`, `WorkoutSession.tsx:134`. Note `addWarmupSets` (`:396-419`) does
   it correctly — it prepends without touching `requiredSets`. Only `startPlanDay` is wrong.

6. [x] **HIGH — fixed.** `buildMission` now resolves the current unit and converts each history entry through `toUnit(st.weight, entry.unit, unit)` before comparing. Originally: *Verified

## Deliberately not done

Each of these was a live option that I decided against. They are choices, not oversights.

- **#62 — the player still does not rotate between superset pairs.** *The only finding not
  fully closed.* It names the partner and says "Alternate sets with X, then rest", so nothing
  is promised that is not delivered, but it does not drive the rotation. Rotating after every
  set changes what a workout *is* and how long it takes, and with no test suite and no way to
  run the app here, shipping an unverified rewrite of the core logging flow is the riskier act.
  **Wants: a device and a real session.**

- **#64 — the exercise log still keys on the library clip's id, not the prescribed movement.**
  The player now *shows* the prescribed name, but history and personal records are built on
  that id. Re-keying it would silently rewrite existing history, which is worse than the
  inconsistency it would fix. **Wants: a migration, if it is ever wanted at all.**

- **#8 — swapping an exercise still attributes already-logged sets to the new movement.** That
  was a deliberate earlier decision (`docs/ux-audit.md`: swapping used to wipe logged sets with
  no undo), so I fixed only the narrower defect — the row count no longer contradicts
  `requiredSets`. Reversing the trade-off is a product call I did not make unasked.

- **#36 — strength, endurance, stamina and mobility were removed rather than derived.** A
  0–100 score under those names reads as a measurement of capability. Gruntz logs what was
  prescribed and ticked; it does not test anyone against a standard. A number built from
  training mix would be a guess wearing the clothes of a measurement, which is worse than an
  empty row. Consistency and recovery are real, so those two stayed.

- **#53 — the streak counter was not changed, only its labels.** `streakGraceDays` exists
  because a strict one-day rule "punished people for following their own plan". The number was
  fair and the words were wrong, so the words changed.

- **#48 — a benchmark record is only credited when the session *was* that distance** (from the
  benchmark to 5% past it). A ten-miler sets no 5K record, because deriving a 5K split from
  average pace would invent a time nobody ran. Inside the window the total elapsed time is
  used, so a record can only ever be conservative.

- **#20 — the empty Android RevenueCat key was left empty.** Correct, given Android is not
  shipping (your call, 2026-09-23). Recorded in `monetization.ts` so it does not read as a bug.
  **If Android ever ships, that key must be set or nobody on Android can subscribe.**

- **#70 — the implausible day estimates were capped for display, not corrected in the data.**
  A 335-minute day still says 335 in `workoutPlans.json`; the screen shows "~120+ min". Fixing
  the catalog belongs in the generator, not the app.

- **#65 — `equipment_access` is reconciled at read time, not regenerated.** Same reason: the
  clip-derived value is still wrong in the data for 22 programs.

- **`npm run check` still fails at its site-build step**, because `website/node_modules` is not
  installed. An environment gap, not a defect — `npm run typecheck`, the part that gates the
  app, is green.
